# 架构革新决策框架

> 来源:用户总结的架构管理经验(AI 项目全栈自管理时代的重要决策准则)。

## 目标

加一个新功能时,做到**最小净增量改动**,且不影响其他模块(解耦合)。

## 决策公式

```
扩展性增益 / 革新工作量
```

## 关键认知

**扩展性增益 ≠ 当前功能价值**。它看的是:未来还会做多少类似的东西?

- 例:"做一个地图" → 不能只看"一张地图提升的可玩性",要追问:**以后会做 5 张?10 张?每张新地图现在要改几个文件?**
- 如果未来 N 个同类需求会让"不改架构的累积成本"远超"一次性重构成本" → 增益高
- 如果只有这一个、未来不扩展 → 增益低

## AI 的职责

遇到可能扩展的功能,**主动问清后续规模**,再决定是否动架构。不假设"只做一次"。

## 执行规则

- 增益低 → 不动架构,在现有结构上堆
- 增益高 → **只动相关部分的架构**,不推翻重来
- 架构革新 ≠ 重写,是局部重构以承载新需求类别
- **不做"顺路重构"无关代码**(重构的扩散要克制)

## 本项目验证案例

| 决策 | 增益评估 | 做法 | 结果 |
|---|---|---|---|
| 游戏厅平台化(platform.js + iframe 隔离) | 高(用户说"童年游戏机",未来 N 张卡带) | 局部重构:加平台壳,游戏自包含 | 坦克/爆破小子零改动接入,后续新游戏只堆新目录 |
| 爆破小子敌人 AI 重做 | 中(该游戏内部迭代) | 直接堆在 main.js | 未动架构,快速见效 |
| 共享 input.js 键位共存 | 高(所有游戏共用输入) | 一次设计,长期复用 | 每个新游戏输入零成本 |

## 反例教训

- 为"踩敌人判定"这类一次性修 bug 动架构 → 会拖慢交付;修 bug 不套用此框架,直接用最小改动。
